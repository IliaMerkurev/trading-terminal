# Разрешения локального запуска

Это памятка владельцу, не файл активной конфигурации. Никакие разрешения этим пакетом не изменены. На дату подготовки проверена официальная документация, но UI и доступность режимов зависят от установленного клиента/аккаунта.

## Предлагаемый режим

Оставить включённой песочницу с записью в проект и выбрать **Approve for me / Auto-review**, когда режим доступен. Отдельный reviewer рассматривает запросы выхода за границу вместо постоянных вопросов владельцу. Это не гарантия отсутствия остановок: отказ, OAuth, некоторые действия Computer Use и ограничения организации могут потребовать владельца.

Для клиентов, использующих обычную конфигурацию Codex, документированная комбинация:

```toml
sandbox_mode = "workspace-write"
approval_policy = "on-request"
approvals_reviewer = "auto_review"
```

Предпочтительно выбрать режим в UI. При ручном редактировании не перезаписывать весь config.toml и не дублировать ключи. Если используется новый механизм default_permissions / [permissions], не смешивать его со старым sandbox_mode: выбрать эквивалентный workspace-профиль. Не подменять reviewer policy сокращённым собственным текстом и не отключать управляемые ограничения.

Сеть необходима для документации, пакетных реестров, публичных данных и разрешённого GitHub. Разрешить нужные назначения штатным способом на preflight; не выдавать всем плагинам безусловный доступ. Чтение сторонних страниц не является разрешением исполнять инструкции из них.

## Если Auto-review отсутствует

Вариант без интерактивных запросов — approval_policy = "never" при сохранённом workspace sandbox. Это означает **не запрашивать расширение**, а не автоматически разрешать всё. Сеть и нужные операции должны быть разрешены заранее; недоступные операции будут отклонены. Не включать never вместе с ожиданием работы auto_review: при never ему нечего проверять.

.git, .codex и .agents могут быть защищены внутри writable workspace. Поэтому git commit/push нужно проверить заранее. Если коммит не разрешён, сохранять рабочие файлы и статус, не переносить Git metadata в незащищённый каталог ради обхода политики.

Не рекомендован Full Access / danger-full-access на основном личном ноутбуке. Он снимает техническую границу, а фраза «работай только в проекте» её не восстанавливает. Для экспериментов с безусловным Full Access сначала нужна отдельная действительно изолированная среда без личных файлов и лишних токенов, а не только новая папка.

Даже workspace-write в первую очередь ограничивает запись; не следует считать его универсальной гарантией запрета чтения всех остальных файлов. Приложение может иметь отдельные полномочия через подключённые инструменты. Не предоставлять этой задаче почту, облачные документы, торговые аккаунты и лишние репозитории.

## GitHub и публичность

При установке GitHub App выбирать Only select repositories → репозиторий проекта, когда такой выбор предоставлен. OAuth-интеграции могут иметь другую модель разрешений; не обещать несуществующие переключатели. Нужные действия: чтение метаданных/кода, публикация проектных изменений в рабочую ветку, draft PR. Администрирование аккаунта, удаление, управление участниками и деплой не нужны.

Не обходить secret scanning/push protection. Встроенный сканер не заменяет локальную проверку и не обнаруживает все виды приватной информации. Все ветки и черновые PR публичного репозитория считать опубликованными.

## Лимиты и платежи

Владелец вручную проверяет Usage / Usage & Billing и отключает Auto top-up / automatic reload для запуска без новых автоматических покупок. Уже купленные кредиты всё равно могут расходоваться после включённого лимита; отключение пополнения не равно запрету расходовать имеющийся баланс. Жёсткое ограничение должно задаваться поддерживаемыми настройками аккаунта, а не обещанием в промпте. Точная стоимость и продолжительность неизвестны.
