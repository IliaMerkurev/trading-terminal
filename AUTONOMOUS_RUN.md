# Trading Terminal — автономный запуск v0.4

**Назначение:** инструкция для локального Codex с выбранной владельцем моделью Astra. Не запускает задачи сама, не меняет разрешения клиента и не является обещанием завершения за ночь.

## 1. Цель и новые полномочия

Владелец хочет эксперимент автономной разработки: самостоятельно принимать инженерные решения и реализовывать V1 из PROJECT.md, а не останавливаться после выбора движка. Код можно публиковать в публичном репозитории самого проекта. Не нужны новые вопросы о каждой библиотеке, файле и следующем этапе.

В пределах согласованного продукта самостоятельно выбирай движок, версии, реализацию адаптера, схему данных, внутренние API, правила расчёта с явными допущениями, структуру тестов и UI. Изменение стартового компонента допустимо при конкретном выигрыше, совместимости требований и ADR. Восстановление будущих тиков из минутных свечей, абсолютная точность Bybit и доходность стратегии не обещаются.

Это отменяет прежние инструкции v0.3 «только исследование движка», «не начинай следующий этап» и «не публикуй без отдельной задачи» в пределах описанного здесь разрешения. Не отменяет реальные ограничения ОС/клиента, безопасность и согласованный состав V1.

## 2. Два этапа запуска

Сначала выполнить PREFLIGHT_ONLY из docs/PREFLIGHT.md, пока владелец может пройти OAuth, доверить папку, установить инструменты и утвердить точный публичный remote. После короткого отчёта остановиться именно для этого предпускового этапа.

После сообщения владельца «Начинай автономный запуск по AUTONOMOUS_RUN.md» продолжать реализацию по этапам, без запросов «продолжать?». Если клиент поддерживает /goal, цель — реализованная и проверенная V1, а не «работай до утра». Без такого режима тот же текст остаётся обычным поручением; длительность и продолжение сессии не гарантируются.

## 3. Разрешено

Создавать, изменять и тестировать код внутри проекта; пользоваться уже установленными инструментами; ставить проверенные необходимые зависимости в изолированные проектные окружения и согласованные кэши; читать первичную документацию; получать открытые исторические данные. Доступ к сети и внешним инструментам — только в рамках настроенных разрешений.

Допускаются новые локальные файлы, схемы, тестовые fixtures, README, ADR, локальные коммиты, рабочая ветка, проверенный push и draft PR в единственный указанный публичный репозиторий. Необходимые локальные серверы UI привязывать к loopback, не открывать их в локальную сеть или через туннели.

Можно самостоятельно исправлять ошибки и переходить к следующему проверяемому этапу. При недостатке информации выбирать простое обратимое решение и записывать его, не утверждая, что владелец отдельно его согласовал.

## 4. Не разрешено

Реальная торговля, private/account endpoints биржи, ключи от бирж и кошельков, API-покупки, пополнение лимитов, платные подписки, покупка данных, облачные ресурсы, регистрация платных сервисов, релизы и деплой. Не переключать текущую сессию на API-биллинг и не включать автоматические списания.

Не менять настройки безопасности Windows/Codex, разрешения, системные службы, реестр, PATH или системные версии инструментов; не обходить отказ разрешения. Системные установки допускаются только отдельно владельцем во время preflight. Не читать другие личные проекты, почту, браузерные данные, ключи и окружения.

Не удалять репозитории, не менять права участников, не использовать force-push/reset --hard/git clean -fdx для удобства. Не запускать неизвестные удалённые install-скрипты вслепую. Не исполнять Python-стратегии из случайных репозиториев: для эксперимента достаточно своего примера либо проверенного минимального официального примера с зафиксированным происхождением.

Не создавать бесконечные циклы, планировщики, автоматический перезапуск агента и не обходить лимиты. Не распараллеливать запись в один working tree.

## 5. GitHub: публичный, но только этот проект

До автономного этапа владелец создаёт или указывает публичный репозиторий. Найди точный URL из сообщения или проверь уже настроенный remote; не угадывай аккаунт по имени автора. При отсутствии однозначного назначения продолжай локально.

Новый пустой локальный Git можно инициализировать. Если ещё нет коммитов, допустим исходный коммит проверенных безопасных документов. Продолжение вести в codex/bootstrap-v1 или другой свободной рабочей ветке. Не перезаписывать существующую ветку с чужими изменениями.

Разрешено публиковать проверенные проектные изменения в эту ветку и открыть draft PR. Сливать в main, менять настройки репозитория и делать release без владельца не нужно. Если push запрещён песочницей или подключение отсутствует, не обходить это: сохранить файлы и доступные локальные checkpoints и продолжать разработку.

Перед первым и каждым последующим push проверять не только текущий diff, но и все ещё не опубликованные коммиты. Проверить секреты установленным надёжным сканером, список публикуемых файлов, личные сведения и права на сторонний код. Отсутствие подписчиков не меняет режим публикации. Ни draft PR, ни отдельная ветка не скрывают код публичного репозитория.

Запрет на отправку .env, токенов, приватных ключей, дампов аккаунтов, личных переписок, сырой истории рынка, пользовательских баз и необработанных логов. .gitignore — профилактика, не очистка уже сохранённой истории. При обнаруженном секрете запретить push и уведомить владельца без повторения самого секрета. Не обходить GitHub push protection.

Конкретная лицензия проекта ещё не утверждена: проверить совместимость выбранного движка и записать рекомендацию. Не подменять публичную доступность заявлением об оформленной open-source лицензии. Сторонние фрагменты и fixtures можно публиковать лишь при понятных разрешениях и соблюдении уведомлений об авторстве.

## 6. Учёт задач

Для этого запуска достаточно docs/TASKS.md и docs/STATUS.md; GitHub хранит проверенные коммиты. Linear не блокирует разработку. Читать уже подключённый Linear можно; создавать/обновлять задачи — только если владелец указал конкретный проект и разрешил записи. Не создавать рабочие пространства и не менять подписку.

При подключённой и разрешённой доске сначала искать существующие задачи, затем обновлять только относящиеся к проекту. Не создавать параллельную доску GitHub Issues. Приёмку интерфейса владельцем не отмечать Done автоматически.

## 7. Порядок реализации

1. Зафиксировать реальные инструменты, окружение, состояние Git и разрешённый remote.
2. Изучить и практически проверить первый движок. После достаточной проверки принять решение; при блокере переключиться на обоснованную альтернативу. Не тратить весь запуск на бесконечное расширение списка кандидатов.
3. Описать вычислительную семантику и контрольные примеры с независимо рассчитанными ожиданиями.
4. Сделать типизированный Strategy IR и один адаптер; внутрикадровая оценка не должна превратиться в стратегию другого таймфрейма.
5. Добавить загрузку данных, покрытие, сохранение снимка запуска и результатов.
6. Получить воспроизводимый бэктест и безопасную отмену в отдельном worker; подключить доверенный Python-импорт.
7. Создать реальный рабочий интерфейс Strategy / Backtest / Results, затем сравнение и экспорт. Не рисовать успешные расчёты вместо их выполнения.
8. Пройти контрольные сценарии, исправить обнаруженные ошибки, подготовить Windows-команду запуска и отчёт для владельца.

При блокере продолжать независимые части. Допустим разработческий UI на явно помеченных синтетических fixtures, но он не считается интегрированным бэктестом. Отсутствующая обязательная функция остаётся открытым требованием, не удаляется из документа.

## 8. Проверки и остановка

На каждом этапе запускай целевые тесты и обновляй docs/STATUS.md. Реальный результат включает команду, exit status/итог, ограничения и следующий шаг. Не выдавай lint за проверку расчётов, mock за рабочую интеграцию, Linux-проверку за Windows-проверку.

Останавливай автономный запуск после реализации и автоматической проверки V1 с подготовленной демонстрацией, либо когда ни одну полезную разрешённую задачу нельзя продолжить из-за реального блокера/доступа/ресурсов. Остановка пользователем и ограничения платформы обязательны. Не требуется ждать утра; нельзя гарантировать, что контекста или лимита хватит до завершения.

Сохраняй checkpoints в течение работы: внезапный обрыв не гарантирует возможность дописать финальный отчёт. Не повторяй одну падающую команду бесконечно; выясняй причину, пробуй иной допустимый подход или отмечай блокер.

Финальный docs/RUN_REPORT.md: реализовано; фактическая команда запуска; тесты и их результаты; неготовые функции; ADR; ветка/commit; проверенный remote/PR; что нужно владельцу. Автоматическая проверка не заменяет личную приёмку. После завершения V1 не начинать отложенный backlog.
